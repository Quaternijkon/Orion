\section{Offline Construction: Coaccessibility-Aware Sharding}
\label{sec:offline_sharding}

To address Challenge\#1, \sysname's offline phase translates the ideal hypergraph min-cut problem into a tractable, three-phase graph partitioning workflow: (1) building and partitioning a sparse \emph{query traffic graph} derived from the data, (2) propagating the resulting partition to the full dataset under a strict size-balance constraint, and (3) selectively replicating boundary points to further reduce fan-out. We first formalize the objective, then detail this pipeline.

\subsection{The Sharding Objective}
Let $X=\{x_1,\dots,x_N\}$ be the dataset, $q\sim Q$ a query drawn from the workload, and $\mathrm{NN}_k(q)\subseteq X$ its true $k$ nearest neighbors under the target metric. A strict sharding is an assignment $\sigma:X\to\{1,\dots,P\}$. To return the true neighbors, a query must touch every shard that holds at least one of them. Thus, its required fan-out is:
\[
\mathrm{fanout}^\star_\sigma(q)=\bigl|\{\sigma(x):x\in\mathrm{NN}_k(q)\}\bigr|.
\]

As established in \S\ref{sec:motivation}, fan-out is the first-order term determining aggregate system work. Our primary objective is to minimize the expected fan-out across the query workload, subject to a strict size balance constraint to distribute storage evenly:
\begin{equation}
\label{eq:objective}
\begin{aligned}
\min_{\sigma}\quad & \mathbb{E}_{q}\!\left[\mathrm{fanout}^\star_\sigma(q)\right] \\
\text{s.t.}\quad & (1-\varepsilon)\tfrac{N}{P}\le |\sigma^{-1}(i)| \le (1+\varepsilon)\tfrac{N}{P}\quad \forall i \in \{1,\dots,P\}.
\end{aligned}
\end{equation}

This objective naturally maps to a hypergraph $H=(X,\{e_q\}_q)$. The vertices are the vector set $X$, and each query's target set forms a hyperedge $e_q=\mathrm{NN}_k(q)$. Intuitively, if a query's target neighbors are scattered across many different shards, its hyperedge is ``cut'' multiple times, forcing the system to fan out to all those shards to retrieve them. Conversely, if all target neighbors are co-located in a single shard, the hyperedge remains uncut and the fan-out is optimal (i.e., 1). Consequently, minimizing the expected fan-out is mathematically equivalent to minimizing the standard connectivity metric (cut) in hypergraph partitioning.

\subsection{Phase 1: Navigation Graph Partitioning}
\label{sec:nav_graph}
Optimizing the ideal hypergraph objective directly is impossible in practice. \emph{Offline}, future queries are unknown, so the exact hyperedges $e_q$ do not exist. Even if they did, the problem is NP-hard and inapproximable~\cite{andreev2006}.

\sysname sidesteps both obstacles by introducing a small, query-independent \emph{query traffic graph} $G=(V,E,w)$ built entirely from the data itself, which acts as a computable structural proxy rather than a direct mathematical replacement for the query hypergraph. Its construction proceeds in three stages---\emph{sample}, \emph{build}, and \emph{color}.

\noindent\textbf{Sample.} Building and partitioning a graph over all $N$ points is prohibitive at billion scale. \sysname instead draws a uniform random subset $V\subseteq X$ of \emph{navigation nodes} (by default $|V|\approx N/32$, i.e.\ $\sim\!3\%$ of the data). This subset acts as a sparse skeleton that captures the global topology of the dataset while keeping the partitioning problem small.

\noindent\textbf{Build.} To estimate how strongly two navigation nodes are \emph{co-accessed} by search, \sysname leverages the dataset itself as a representative query workload. Concretely, it builds an auxiliary HNSW index over the navigation nodes $V$ and, for every data point $x\in X$, issues a $k$-nearest-neighbor query against it ($k{=}10$ by default). The returned nodes form $x$'s \emph{attachment set} $A(x)\subseteq V$---the navigation nodes through which a search seeded at $x$ would be routed. Aggregating these sets over the entire dataset defines a \emph{query traffic graph} $G=(V,E,w)$ whose edge weight counts how often two nodes are attached by the same point. The \emph{navigation traffic} on an edge $(u,v)$ is:
\begin{equation}
\label{eq:traffic}
w(u,v)=\mathbb{E}_{q\sim X}\bigl[\,\#\{\text{times } u \text{ and } v \text{ are co-attached by } q\}\,\bigr].
\end{equation}
The working hypothesis (\emph{search-induced topology}) is that $w$ is an accurate, computable proxy for co-relevance: points reached together during navigation tend to fall in a common query's target set. Crucially, $w$ is derived entirely from search behavior (co-attachment), not from raw geometric distance. This is the only signal the partitioner consumes---no query log or ground-truth neighbor is ever required---and it is what the offline objective below actually minimizes as the \emph{attachment cut}.

\noindent\textbf{Color.} Finally, \sysname \emph{colors} the query traffic graph, assigning each node $v\in V$ a shard label $\pi(v)\in\{1,\dots,P\}$. Under this surrogate, the intractable hypergraph min-cut reduces to a standard \emph{weighted graph edge-cut}: minimize $\sum_{(u,v):\pi(u)\neq\pi(v)} w(u,v)$ subject to the balance band of Eq.~\eqref{eq:objective}. \sysname solves it with a lightweight two-phase procedure. First, a \emph{standard geometric $K$-means} over $V$ produces a locality-preserving initial coloring; the seed only needs to supply geometric coherence, since---as we show in \S\ref{sec:eval}---the deliverable fan-out is insensitive to how (or whether) the seed itself is balanced. Second, an iterative \emph{majority-vote label propagation} refines it: each node moves to the shard holding the majority of its attachment neighbors, directly lowering the attachment cut. Crucially, this refinement is where size balance is actually enforced. Each navigation node is weighted by its \emph{projected load}---the number of base-layer points that will later attach to it---and \sysname tracks the aggregate weight of every shard. A topology-improving move is admitted only if it leaves the source shard above the lower bound and the target shard below the upper bound of the balance band; whenever a shard drifts out of band, a bounded \emph{balance-repair} move (tolerating a small, capped loss in the cut) pulls it back. Because every base point ultimately inherits the color of the navigation node it attaches to, balancing this projected load on the $\sim\!3\%$ skeleton is exactly what yields size balance on the full dataset (\S\ref{sec:base_assignment}). Balance is thus owned by the refinement, not the seed, which lets \sysname adopt the simplest possible initializer.

Note that this refinement is a purely \emph{node-local} operation---it collocates each node with its own attachment neighbors---and never enumerates any query's neighbor set. It is precisely the tractable surrogate for the ideal, but intractable, objective of Eq.~\eqref{eq:objective}: driving down the attachment cut co-locates points that are co-accessed together, which Lemma~\ref{lem:fanout} shows bounds the very per-query fan-out that Eq.~\eqref{eq:objective} seeks to minimize.

Once the coloring $\pi$ is finalized, \sysname builds the actual \emph{navigation graph} (an HNSW index) over the colored nodes $V$. This graph is used during online search to query the neighborhood of the target and determine the shard distribution of the nearest navigation nodes.

The following lemma justifies the reduction: the weighted cut that \sysname minimizes upper-bounds the online fan-out it actually pays.

\begin{lemma}[Realized fan-out is bounded by the attachment cut]
\label{lem:fanout}
Let $\mathrm{cut}(\pi)=\{(u,v)\in E:\pi(u)\neq\pi(v)\}$ be the edges cut by the coloring $\pi$ in the query traffic graph. If a query's entry points are drawn from its attachment set, the expected realized fan-out is bounded by:
\[
\mathbb{E}_{q}\!\left[\mathrm{fanout}^\pi(q)\right]
\ \le\ 1+\!\!\sum_{(u,v)\in\mathrm{cut}(\pi)}\!\! w(u,v).
\]
\end{lemma}

\begin{proof}
For a query $q$, let $A(q) \subseteq V$ be its attachment set (the navigation nodes it co-accesses). By definition, the realized fan-out is the number of distinct shards covering $A(q)$, denoted $m = |\{\pi(v) : v \in A(q)\}|$. Consider the complete subgraph formed by $A(q)$ in the query traffic graph. To span $m$ distinct shards, this subgraph must contain at least $m-1$ edges whose endpoints lie in different shards (i.e., cut edges). Therefore, $m \le 1 + |\{(u,v) \in A(q) \times A(q) : \pi(u) \neq \pi(v)\}|$. Taking expectations over $q$ and applying the definition of $w(u,v)$ from Eq.~\eqref{eq:traffic} yields the bound. Note that this is a conservative upper bound, as $A(q)$ may contain many more than $m-1$ cross-shard edges.
\end{proof}

\subsection{Phase 2: Base-Layer Assignment}
\label{sec:base_assignment}
The coloring $\pi$ labels only the navigation skeleton $V$ ($\sim\!3\%$ of the data); \sysname must now extend it to all $N$ points. Each base-layer (L0) point is placed by the very same attachment signal: it inherits the shard labels of the navigation nodes it attaches to and is assigned to the majority shard. This propagates the low-cut partition from the sparse skeleton to the full dataset at near-linear cost, without ever materializing a graph over all $N$ points.

\noindent\textbf{Enforcing exact size balance.} Phase~1 balances only the \emph{projected} load carried by the skeleton, so the realized L0 counts can still drift from the balance band. \sysname closes this gap with a capacity-constrained assignment pass: it caps each shard's point count at the upper balance bound, and for any point whose top-voted shard is already full it spills the point to the next shard supported by its \emph{own} attachment evidence, resolving any residual violation with a min-cost flow over these evidence-admissible reassignments. The outcome is a full-dataset partition that satisfies the size band of Eq.~\eqref{eq:objective} exactly while preserving the low attachment cut.

\noindent\textbf{Why the balance band matters for load.} The size balance band of Eq.~\eqref{eq:objective} is not merely a storage convenience---it is what keeps query load in check. Left unconstrained, the min-cut objective would pull every frequently co-accessed ``hub'' region into a single shard, since keeping hubs together is exactly what minimizes the cut. That shard would then lie on almost every query's path, so even a router that fans out across many shards could not spread its load. Our ablation confirms this failure mode: dropping the band lowers mean fan-out (fewer, larger shards to probe) yet inflates load skew so severely that end-to-end throughput \emph{drops} (\S\ref{sec:eval}). Enforcing the band is therefore the mechanism that prevents hub collapse and keeps the layout spreadable by the router in the first place.

\emph{Concretely, hub dispersal falls directly out of the projected-load weighting of Phase~1.} A hub navigation node is, by definition, one that a disproportionate number of base points attach to, so it carries a large projected load. Because the capacity band caps each shard's \emph{aggregate} projected load, no single shard can absorb more than a few such heavy hubs before saturating its upper bound: any refinement move that would pile another hub onto a saturated shard is rejected, and a balance-repair move actively evicts hub mass until the shard falls back into band. Co-accessed hubs are thereby forced apart onto \emph{distinct} shards rather than collapsed together---even though the raw min-cut objective would prefer to keep them on one. Phase~2 then preserves this dispersal at the base layer: the same per-shard point-count cap prevents the majority-vote assignment from re-concentrating a hub's followers onto its home shard, spilling the overflow to the next shard their own attachment evidence supports. With the hot hubs now living on \emph{different} shards rather than one, no single shard sits on every query's path: each query's fan-out lands on its own handful of shards, so the aggregate traffic---routed online by the fan-out router (\S\ref{sec:online})---spreads across the cluster instead of piling onto one hot shard. (Replication in Phase~3 later adds a complementary lever, letting the router cover a single hot hub from the least-loaded of \emph{its} several copies.)

Beyond enforcing this band, however, finer load-specific balancing is neither necessary nor effective. Tightening size balance further, or relocating base points by their estimated hub load, barely moves load skew---it is governed by where queries cluster, not by exact shard sizes---while sacrificing locality and inflating fan-out (\S\ref{sec:eval}). \sysname therefore enforces the balance band and stops there: within the band, the router's fan-out already distributes hub traffic, leaving only a second-order residual skew (under $2\times$; \S\ref{sec:online}) that warrants no additional offline effort.

\subsection{Phase 3: Data Multi-Assignment}
\label{sec:multiassign}
So far, $\sigma$ assigns each point to a single shard, which corresponds to an \emph{edge-cut} formulation. However, graph partitioning theory offers a powerful relaxation: the \emph{vertex-cut} (or overlapping) formulation. 

By allowing a point to be assigned to multiple shards ($\sigma:X\to 2^{\{1,\dots,P\}}$), we can replicate points that sit on heavily trafficked boundaries. This mathematically reduces the cut size, as queries no longer need to cross a partition boundary to reach a replicated neighbor. \sysname operationalizes this with the same attachment votes used in Phase~2: a point is a \emph{boundary point} when its attachment set does not concentrate on a single shard but instead ties (or nearly ties) across several. Rather than forcing such a point onto one majority shard, \sysname places a replica on \emph{every} shard within a small vote margin of the top---up to a bounded, user-configurable replica count. This strictly lowers the required fan-out without sacrificing recall, at the cost of a controlled storage expansion.

As a secondary benefit, replicating a hot neighborhood onto several shards also gives the online router freedom to cover a query from whichever replica is least loaded, which can further trim the already-modest residual load skew; but the primary and validated gain is the reduction in fan-out.

With the offline index constructed and partitioned, the remaining challenge is how to efficiently route online queries against this topology. We detail \sysname's online navigational routing in the next section.
